# Database Migrations

This project uses [Alembic](https://alembic.sqlalchemy.org/) to manage PostgreSQL schema changes. Migration scripts live in `alembic/versions/` and are version-controlled with the application code.

## Prerequisites

- PostgreSQL database reachable from your environment
- `DATABASE_URL` set to a PostgreSQL connection string, for example:

```bash
export DATABASE_URL=postgresql+asyncpg://user:password@localhost:5432/dbname
```

Sync URLs (`postgresql://...`) are also accepted; Alembic and the app convert them to `postgresql+asyncpg://` automatically.

Environment files checked (in order):

1. `.env` (project root)
2. `src/.env`
3. `.env.test` (used in local/test environments)

Copy `src/.env.example` to `src/.env` and adjust values for your machine.

## Quick Start

```bash
# 1. Set up your database connection
cp src/.env.example src/.env
# Edit src/.env with your PostgreSQL credentials

# 2. Apply all migrations
alembic upgrade head

# 3. Verify
alembic current
```

## Common Commands

Run all commands from the project root.

### Apply all pending migrations

```bash
alembic upgrade head
```

### Roll back one migration

```bash
alembic downgrade -1
```

### Roll back to a specific revision

```bash
alembic downgrade 001_initial
```

### Roll back all migrations

```bash
alembic downgrade base
```

### Show current revision

```bash
alembic current
```

### Show migration history

```bash
alembic history --verbose
```

### Generate a new migration from model changes

After updating SQLAlchemy models in `src/models/`, autogenerate a revision:

```bash
alembic revision --autogenerate -m "describe your change"
```

Review the generated script before committing it.

### Generate an empty migration

```bash
alembic revision -m "manual schema change"
```

## CLI Wrapper

A convenience CLI script is provided at `scripts/migrate.py` for consistent multi-environment usage:

```bash
# Apply all pending migrations
python scripts/migrate.py upgrade

# Roll back one step
python scripts/migrate.py downgrade

# Roll back all
python scripts/migrate.py downgrade base

# Show current revision
python scripts/migrate.py current

# Show history
python scripts/migrate.py history

# List pending (unapplied) migrations
python scripts/migrate.py pending

# Generate a new autogenerated migration
python scripts/migrate.py generate "add orders table"

# Generate an empty migration
python scripts/migrate.py generate "manual fix" --empty

# Stamp the DB at a revision without running migrations
python scripts/migrate.py stamp head

# Check database connectivity
python scripts/migrate.py check
```

The CLI prints the current environment and sanitized database host before each operation.

## Environment-Specific Usage

### Development

1. Start PostgreSQL locally.
2. Create a database (for example `project_dev`).
3. Set `DATABASE_URL` in `.env` or `src/.env`.
4. Run `alembic upgrade head`.
5. Start the API with `uvicorn main:app --app-dir src --reload`.

Migrations also run automatically on application startup when `AUTO_MIGRATE=true` (the default).

### Staging

1. Export `DATABASE_URL` for the staging database.
2. Set `ENVIRONMENT=staging` to enable staging-appropriate pool sizes.
3. Run migrations before deployment:

```bash
ENVIRONMENT=staging DATABASE_URL=postgresql+asyncpg://... alembic upgrade head
```

4. Disable auto-migration in the application:

```bash
AUTO_MIGRATE=false uvicorn main:app --app-dir src --host 0.0.0.0 --port 8000
```

### Production

1. Export `DATABASE_URL` for the production database (use CI secrets, Kubernetes ConfigMaps, etc.).
2. Set `ENVIRONMENT=production`.
3. **Always run migrations explicitly** in a deployment step — never rely on `AUTO_MIGRATE` in production:

```bash
AUTO_MIGRATE=false alembic upgrade head
```

4. Verify the applied revision:

```bash
alembic current
```

5. Start the application with auto-migration disabled:

```bash
AUTO_MIGRATE=false uvicorn main:app --app-dir src --host 0.0.0.0 --port 8000
```

Never edit migration files that have already been applied in shared environments. Add a new revision instead.

## CI/CD Integration

### GitHub Actions Example

```yaml
jobs:
  migrate:
    runs-on: ubuntu-latest
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_USER: ci
          POSTGRES_PASSWORD: ci
          POSTGRES_DB: testdb
        ports:
          - 5432:5432
        options: >-
          --health-cmd pg_isready
          --health-interval 10s
          --health-timeout 5s
          --health-retries 5

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run migrations
        env:
          DATABASE_URL: postgresql+asyncpg://ci:ci@localhost:5432/testdb
        run: alembic upgrade head

      - name: Verify migrations
        env:
          DATABASE_URL: postgresql+asyncpg://ci:ci@localhost:5432/testdb
        run: alembic current

      - name: Run migration tests
        env:
          DATABASE_URL: postgresql+asyncpg://ci:ci@localhost:5432/testdb
        run: pytest src/tests/test_migrations.py -v
```

### Docker Entrypoint Example

```bash
#!/bin/bash
set -e

# Run migrations before starting the app
alembic upgrade head

# Start the application
exec uvicorn main:app --app-dir src --host 0.0.0.0 --port 8000
```

## Integration with FastAPI

- SQLAlchemy models are defined under `src/models/`.
- `alembic/env.py` imports `models` so `Base.metadata` includes every table.
- `src/config/database.py` exposes `engine`, `async_session_factory`, and the `get_db_session` dependency for route handlers.
- `src/config/migrations.py` provides `run_migrations()` used during application startup and a full migration management API (`downgrade_migrations`, `get_current_revision`, `has_pending_migrations`, etc.).
- `src/config/environment.py` provides `Environment` enum and pool configuration based on the deployment target.

### Auto-Migration on Startup

When the app starts, `main.py` checks `AUTO_MIGRATE`:

- `true` (default): Runs `alembic upgrade head` in a thread before serving requests.
- `false`/`0`/`no`/`off`: Skips migrations — useful when they run in a separate deployment step.

### Health Check Endpoints

| Endpoint | Description |
| --- | --- |
| `GET /health` | Basic liveness check |
| `GET /health/db` | Database connectivity + migration status (current revision, head revision, pending migrations) |

Disable automatic migrations when running them explicitly in CI/CD:

```bash
AUTO_MIGRATE=false uvicorn main:app --app-dir src --host 0.0.0.0 --port 8000
```

## Environment Variables

| Variable | Default | Description |
| --- | --- | --- |
| `DATABASE_URL` | — | PostgreSQL connection string (required) |
| `DB_URL` | — | Alias for `DATABASE_URL` |
| `ENVIRONMENT` | `development` | Deployment environment (`development`, `staging`, `production`, `testing`) |
| `AUTO_MIGRATE` | `true` | Run migrations on app startup |
| `DB_POOL_SIZE` | varies by env | SQLAlchemy connection pool size |
| `DB_POOL_MAX_OVERFLOW` | varies by env | Max overflow connections |
| `DB_POOL_RECYCLE` | — | Connection recycle time in seconds |
| `DB_ECHO` | `false` | Log all SQL statements |

## Migration History Output

The `history` command (and `scripts/migrate.py history`) shows each revision with markers:

- `+` indicates the revision has been applied to the database
- `*` indicates the revision is the current database head

Example output:

```
 +* 001_initial — Initial migration: create users table

  + = applied, * = current database revision
```

## Initial Schema

Revision `001_initial` creates the `users` table with:

- `id` (integer, primary key, autoincrement)
- `email` (varchar 255, unique, indexed)
- `hashed_password` (varchar 255, not null)
- `created_at` (timestamp with timezone, server default `now()`)
- `updated_at` (timestamp with timezone, server default `now()`)

## Creating New Migrations

1. Update or add SQLAlchemy models in `src/models/`.
2. Import any new models in `src/models/__init__.py` so `Base.metadata` picks them up.
3. Generate a revision:

```bash
alembic revision --autogenerate -m "describe your change"
```

4. **Review** the generated file in `alembic/versions/` — autogenerate is not perfect.
5. Test locally: `alembic upgrade head && alembic downgrade -1 && alembic upgrade head`.
6. Commit the migration file to version control.

## Troubleshooting

| Issue | Resolution |
| --- | --- |
| `DATABASE_URL is not configured` | Export `DATABASE_URL` or create `.env` from `src/.env.example`. |
| `Can't locate revision` | Ensure you are on the latest code and run `alembic upgrade head`. If the DB references a deleted revision, run `python scripts/migrate.py stamp head`. |
| Autogenerate misses tables | Import new models in `src/models/__init__.py`. |
| Async driver errors | Use `postgresql+asyncpg://` or let the app normalize `postgresql://` URLs. |
| Migration already applied | Never edit applied migrations. Create a new revision instead. |
| Pool exhaustion in production | Tune `DB_POOL_SIZE` and `DB_POOL_MAX_OVERFLOW` via environment variables. |
| Permission denied | Ensure the database user has `CREATE TABLE`, `ALTER TABLE`, and `DROP TABLE` privileges. |
